# 데이터 원천과 이용 근거

## 원칙

1. **기술적으로 가능하다는 것은 이용 허락이 아닙니다.** 사이트가 응답한다는
   사실만으로 어댑터를 켜지 않습니다.
2. **비공개 내부 통신 주소를 공식 API로 가정하지 않습니다.** 개발자 도구에
   보이는 XHR 주소는 계약이 아니라 구현 세부사항입니다. 예고 없이 바뀌고,
   이용약관이 없으며, 사용을 승인받은 적도 없습니다.
3. **이용허락이 필요한 어댑터는 기본 비활성이고, 그 사실을 앱 안에서
   사용자에게 밝힙니다.** 조용히 꺼두지 않습니다.
4. **출처 없는 레코드는 저장 경로 자체가 없습니다.** `ProvenanceColumns` 는
   선택이 아닙니다.

## 1. WBAK · KBSA — 왜 차단인가

### 상태: `blocked`, 환경 변수만으로는 켤 수 없음

**WBAK** (`lib/data/sources/adapters/permission_gated_adapters.dart`):

> WBAK의 외부 공개 API가 확인되지 않았습니다. 이용허락을 받기 전까지 자동
> 수집을 하지 않습니다.

**KBSA**:

> KBSA 통합경기정보의 공개 API가 확인되지 않았습니다. 이용허락 또는 CSV 제공 시
> 활성화합니다.

이 문구는 주석이 아니라 `disabledReasonKo` 이며, **앱의 데이터 출처 화면에
그대로 표시됩니다.** 사용자가 "왜 우리 리그 일정이 없냐"고 물었을 때의 답이
앱 안에 있습니다.

### 이중 잠금

플래그 하나로 켤 수 없게 만든 것이 의도입니다.

| 층 | 잠금 |
| --- | --- |
| 앱 | `WB_FLAG_ADAPTER_WBAK` / `_KBSA` 기본 `false` |
| 수집 스크립트 | `scripts/ingest/fetch_sources.py` 의 `blocked_reason` 이 **하드코딩** |
| CI | `publish-data.yml` 의 env 목록에 `WB_INGEST_WBAK/KBSA` 가 **아예 없음** |

두 번째 층이 핵심입니다. `blocked_reason` 이 있는 한 `--all` 로 돌려도 건너뜁니다.
이걸 지우려면 코드를 고치고 리뷰를 받아야 합니다. **환경 변수 하나 잘못 켜서
남의 사이트를 긁는 사고**가 나지 않도록 한 것입니다.

### 켜는 절차

1. 서면 이용허락(이메일 회신도 가능) 확보. **API·CSV 제공이면 더 좋습니다.**
2. 이 문서에 근거를 기록: 누가, 언제, 무엇을, 어떤 조건으로 허락했는지.
3. `fetch_sources.py` 의 해당 `blocked_reason` 제거 — **리뷰 필수**.
4. 어댑터의 `enabled` 를 플래그로 열고 `licenseStatus` 를 갱신.
5. `WB_INGEST_WBAK` 를 GitHub Variables에 추가.
6. 요청 간격과 `robots.txt` 를 지키는지 확인.

순서를 바꾸지 마세요. 특히 1번보다 3번을 먼저 하지 마세요.

### 그동안의 대안

**사람이 넣는 데이터.** Google Forms로 팀·일정·결과를 제보받고, 검수한 뒤
게시합니다. 느리지만 합법이고, 출처가 명확하며, 틀렸을 때 정정 경로가 있습니다.
자세한 내용은 `docs/google-forms.md`.

## 2. WBSC · WPBL — 왜 아직 비활성인가

차단은 아닙니다. 공개 페이지가 있습니다. 다만:

- **WBSC**: 응답 구조 검증과 실패 격리를 마친 뒤 켭니다. 국제대회는 대회마다
  포맷이 달라서, 검증 없이 켜면 이상한 레코드가 조용히 들어옵니다.
- **WPBL**: 공개 GET 주소가 있으나 **장기 제공이 보장되지 않습니다.** 어느 날
  사라져도 앱이 멀쩡해야 하므로, 스키마 검증과 함께 켭니다.

현재 저장소의 WBSC 관련 실제 레코드(단체 1건, 2026 여자야구 월드컵 1건)는
자동 수집이 아니라 **공식 페이지를 보고 사람이 넣은 것**이며, `sourceUrl` 에
그 페이지가 적혀 있습니다.

## 3. 뉴스 — 무엇을 저장하고 무엇을 저장하지 않는가

**저장합니다**: 제목, 매체(호스트명), 발행시각, 원문 URL, **API가 제공한 설명**.

**저장하지 않습니다**: 기사 본문, 언론사 이미지, 사람이 쓰지 않은 요약.

요약 정책이 특히 중요합니다. `scripts/normalize/normalize.py` 는 제목을 보고
"무슨 일이 일어났는지"를 쓰지 않습니다. 만드는 문장은 **셀 수 있는 것만**
말합니다.

> "3개 매체가 같은 사안을 보도했습니다. 각 매체의 원문에서 자세한 내용을 확인할
> 수 있습니다."

매체가 하나뿐이면 요약을 만들지 않고 제목만 보여줍니다. 그리고 자동 생성물은
전부 `reviewStatus: "pending"` 입니다 — **자동화는 후보만 만들고, 사람이
승격시킵니다.**

### 군집화의 실제 한계

`story_key` 는 제목의 **의미 있는 단어 집합이 정확히 일치할 때만** 같은 사안으로
묶습니다. 단어 하나만 달라도 별개 묶음이 됩니다.

```
"채널A 야구여왕 시즌2 제작 확정"          → 묶음 A
"야구여왕 시즌2 제작 확정, 채널A 편성"     → 묶음 B  (단어 하나 차이)
```

**의도한 방향은 맞습니다** — 관계없는 두 기사를 합치는 것이 따로 두는 것보다
나쁩니다. 다만 실제 헤드라인은 매체마다 한두 단어씩 다르므로, **운영에서는
묶음이 seed 데이터보다 훨씬 잘게 쪼개집니다.** seed의 3개 매체 1묶음은 사람이
직접 묶은 것이지 이 알고리즘의 출력이 아닙니다.

이 동작은 `scripts/tests/test_normalize.py` 에 테스트로 고정돼 있습니다.
임계값을 바꾸려면 잘못 합쳐지는 사례를 먼저 확보한 뒤 바꾸세요.

### 팀 별칭

같은 팀을 여러 표기로 부르므로 별칭 색인을 씁니다(정규화형 + 초성).
**모르는 표기는 추측하지 않습니다.** `review/unknown-aliases.json` 으로 보내고
사람이 판단합니다. 관계없는 두 기사를 한 묶음으로 만드는 것이, 따로 두는 것보다
나쁩니다.

## 4. 날씨 — 예보 가능 범위를 넘지 않는다

기상청이 예보하지 않는 것을 앱이 만들어내지 않습니다.

| 범위 | 표시 |
| --- | --- |
| D+0 ~ D+2 | 단기예보. 기온·강수확률 등 상세 |
| D+3 ~ D+10 | 중기예보. 범위와 경향 |
| D+11 이상 | **일정만.** 날씨 칸 자체가 없음 |

`ForecastHorizon` 이 무엇을 렌더링해도 되는지 결정하고,
`WeatherRisk.evaluate()` 는 D+10을 넘으면 `unknown` 을 돌려줍니다.
위험 임계값은 기상청 특보 기준을 인용합니다.

마이야구의 30일 일정판이 이 규칙의 시험대입니다. **30일치 일별 날씨를 보여주고
싶은 유혹이 가장 큰 화면**이고, 그래서 명시적으로 막았습니다.
`test/unit/weather_horizon_test.dart` 가 확인합니다.

주의: 예보가 단순히 저장되지 않은 경우와, 예보 가능 범위 밖인 경우는 다릅니다.
전자는 아무것도 표시하지 않고, 후자만 "예보 범위 밖"이라고 말합니다.
(초기 구현에서 이 둘을 섞어 "상세 예보 전"이 엉뚱한 날짜에 뜨는 버그가 있었습니다.)

## 5. 데모 데이터

- 전부 `isDemo: true`, `sourceName: "demo-fixture"`,
  `sourceUrl: "app://demo/fixture"`.
- **선수 72명은 생성된 픽스처입니다.** 이름은 `데모선수 1-1` 형식이고, 레코드
  필드는 `id`·`name`·`isMinor`·`source` 넷뿐입니다. 생년월일·연락처·사진을 담을
  자리가 스키마에 없습니다.
- **타격·투구 기록은 경기 id로 시드를 고정한 난수입니다**
  (`_box_score` in `scripts/publish/build_seed.py`). 실제 성적을 옮긴 것이
  아니며, 제약은 사실성이 아니라 정합성입니다 — 타자 득점 합이 팀 점수와 맞고,
  상대 투수 실점이 그 점수와 맞아야 검증기를 통과합니다.
- 팀·경기장·선수 이름은 **실존 팀과 혼동되지 않도록** 지어졌고, 경기장 이름에는
  `(데모)` 가 붙습니다.
- 목록과 상세 **양쪽**에 `데모` 배지가 붙습니다.
- 야구여왕 시즌 2의 **회차 결과나 최신 회차를 임의로 쓰지 않았습니다.** 프로그램과
  시즌 메타데이터(제목·공식 페이지 링크)만 실제이고, 회차는 `데모 회차` 하나뿐이며
  `isDemo: true` 입니다.
- 운영 배포 게이트가 이를 강제합니다:

```bash
python scripts/validate/validate_data.py public-data --production
```

## 6. 검증기가 막는 것

`scripts/validate/validate_data.py`:

- 구조와 스키마 적합성
- **출처 누락** — 출처 없는 레코드는 통과 못 함
- 이닝 합계와 최종 점수의 불일치
- 중복 (`Game.dedupeKey()`)
- **개인정보 필드** — 전화번호·주소·개인 이메일·정확한 생년월일.
  단, 경기장의 `address` 는 시설 정보이므로 허용합니다. 연락처 필드와 사람 필드를
  분리해서 판정합니다. (초기 구현이 경기장 주소를 개인정보로 오판했습니다.)
- **예보 범위 규칙** — D+10을 넘는 일별 값이 있으면 실패
- **박스스코어 정합성** — 안타 > 타수, 장타 합 > 안타, 자책점 > 실점,
  타자 득점 합 ≠ 팀 점수, 상대 투수 실점 합 ≠ 팀 점수 는 모두 실패
- **데모 분리** — `--production` 에서 `isDemo: true` 가 하나라도 있으면 실패
