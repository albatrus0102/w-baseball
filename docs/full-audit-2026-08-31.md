## 이 검수가 만들 때와 다르게 한 것

만들 때의 방법은 "코드를 읽고 결함을 찾는다"였다. 같은 방법을 두 번 쓰면 같은 답을 두 번 얻으므로,
이번에는 네 가지를 썼다.

1. **수치 측정** — 눈이 아니라 오버플로 픽셀 수. 17개 화면 × 3배율.
2. **기준 커밋과 양방향 대조** — 감사 시작 전 커밋(`bedc6ef`)을 별도 워크트리에 꺼내 **같은 계측을
   양쪽에 겨눠** 돌렸다. "고친 것이 걸리는가"뿐 아니라 **"안 고쳐야 할 것이 안 걸리는가"**를 본다.
3. **물려받은 상수·전제 재검증** — 이번에 안 바뀐 코드의 숫자와, 이번 변경이 올라탄 전제.
4. **문서 대조** — 문서가 주장하는 수치를 그대로 실행해서 확인.

### 판정 도구부터 검증했다

계측에 **반드시 넘쳐야 하는 대조군**(폭 900px 고정 상자)을 함께 넣었다. 세 배율 모두에서 540px
넘침으로 검출됐다. 대조군이 잡히지 않았다면 그 회차의 모든 `OK`는 무의미했을 것이다.

## 발견

### [F-1] 글자 배율 결함이 6개 화면에 남아 있고, 이를 감시한다는 테스트에는 단정문이 없다

**측정값** (360dp, 실시계):

| 화면 | 1.0x | 1.4x | 2.0x |
|---|---|---|---|
| 순위표 | OK | **12px 우측** | **142px 우측** (`_ActionsScope` — 앱바 액션 영역) |
| 일정판 | OK | **2.8px 하단** | **34px 우측**(`_MonthHeader`) + 20px·49px 하단 |
| 홈-현역 | OK | OK | **60px 우측** (`WbSourceLine`) |
| 대회 | OK | OK | **52px 우측** (`WbSourceLine`/`WbCard`) |
| 근처경기 | OK | OK | **16px 하단** (`WbEmptyState`) |
| 나머지 11개 | OK | OK | OK |
| 대조군 | 540px | 540px | 540px |

**왜 안 잡혔나.** `test/audit/text_scale_probe_test.dart`의 두 번째 루프(1.3/1.4/1.7/2.0 ×
홈·경기·마이야구)에는 **`expect`가 하나도 없다.** `debugPrint`만 한다 — 절대 실패할 수 없는
테스트다. 단정하는 것은 첫 번째 루프의 `홈-입문자 @ 1.4x` 하나뿐이다.
그리고 프로브가 재는 화면은 **17개 중 3개**다. 순위표·일정판·대회·근처경기는 어떤 배율에서도
측정된 적이 없다.

**문서와 어긋남.** `docs/post-build-audit.md:40`은 P1-7을 이렇게 기록한다 —
`상한 1.4 → 2.0. 360dp에서 1.3/1.4/1.7/2.0 전부 통과, 단정 테스트`.
"단정 테스트"는 사실이 아니고, "전부 통과"도 현재 사실이 아니다.
(작성 시점에는 참이었을 수 있다 — 홈의 넘침은 데이터 신선도에 달려 있고, 그건 시간이 지나면
바뀐다. 그렇다면 **조용히 만료된 주장**이며, 그게 더 나쁘다.)

**원인 확정 (`WbSourceLine` 건).** `Row(mainAxisSize: min)` 안에서 텍스트만 `Flexible`이고
배지 두 개(`오래된 정보`, `데모 데이터`)는 줄어들지 않는다. 배지를 빼고 재측정하면 1.7x·2.0x
넘침이 **모두 사라지고**, 되돌리면 다시 나타난다.
순위표·일정판·근처경기의 원인은 **아직 확정하지 않았다** — 증상만 측정했다.

**책임 소재.** 기준 커밋(`bedc6ef`)에서 같은 계측을 돌린 결과가 **픽셀 수까지 완전히 동일**하다.
이번 15개 커밋 중 어느 것도 이 결함을 만들거나 악화시키지 않았다. A-13에서 늘린 순위표 문구도
수치를 바꾸지 않았다(넘침은 앱바 액션 영역이지 문구가 아니다).

### [F-2] 출하된 앱은 설치 순간부터 영구히 "오래된 정보"를 표시한다

**측정값**:
```
manifestBaseUrl=""   isConfigured=false   staleAfter=12:00:00
홈 화면 오래된정보 배지 = 1   (시드 generatedAt 2026-08-30T00:00Z, 측정 시각 16:36Z)
```

동기화 원본이 기본값으로 비어 있으므로 `fetchedAt`은 **빌드 시각에 고정**된다. 12시간이 지나면
모든 카드에 `오래된 정보`가 붙고, 앱 안에서는 그것을 해소할 방법이 없다 — 받아올 곳이 없기
때문이다.

이건 두 가지가 겹친 자리다. 사용자에게는 앱이 자기 데이터를 못 믿겠다고 계속 말하는 것으로
보이고, 동시에 **이 배지가 F-1의 홈·대회 넘침을 유발하는 바로 그 위젯**이다.

판단이 필요한 부분이라 방향을 제시하지 않는다 — 배포본을 붙일 것인지, 배포본이 없을 때
`staleAfter`를 다르게 볼 것인지, 시드에 한해 다른 문구를 쓸 것인지는 제품 결정이다.

## 하지 않은 것과 그 이유

- **수정하지 않았다.** 감리자는 만들지 않는다. F-1의 `WbSourceLine` 한 줄짜리 수정도 하지 않았다.
- **순위표·일정판·근처경기의 원인을 확정하지 않았다.** 증상만 측정했다. 재현 없이 원인을 적으면
  그럴듯한 오진이 문서에 남는다.
- **APK 크기(69MB / 199MB) 주장을 확인하지 않았다.** 릴리스 빌드가 필요하고, 90초 규칙에 걸린다.
  미검증으로 남긴다.
- **실기기 부팅으로 확인하지 않았다.** 위젯 테스트 렌더링과 실기기 렌더링은 다를 수 있으므로,
  F-1의 픽셀 수는 **실기기 실측이 아니다.**
